# E18 — Preloaded queue design and disputed delegation boundary

Record version: DES-218.2. Owner: Delivery Assurance lead Ivo Santos. Dated: 2025-06-12 12:50 UTC. Status: technical design note and narrow permission; production routing remains inactive.

Ivo reviewed a proposed twenty-order preloaded work queue. Vela would select order references, disable their legacy transmission, then have an operator inspect each row and click release after checking quantity. The design has two possible implementations. In mode A, clicking release calls the new connector, which creates a warehouse reservation and records an acknowledgment. In mode B, the queue only presents a work instruction, and the Vela operator enters the order through the existing warehouse screen. These modes have different automation and evidence implications. The current mockup looks the same in both modes and its screenshot cannot establish which code path is configured.

Jules's staging build currently implements mode A. Ivo believes that one-by-one human release might fit AUTH-7's nonautomated demonstration delegation because no event runs without a human action. Nia's approval record describes a supervised commercial pilot requiring joint signatures. Ivo has not countersigned that record or received Nia's specific classification of mode A. He asks whether the term nonautomated concerns unattended processing or any new automated downstream transaction. Counsel's earlier note flags this distinction but does not settle the implementation. The project needs the named authority to interpret the actual mode, not a new title on the user interface.

Ivo authorizes isolated staging validation of mode A this afternoon. He does not authorize production routing in this note. The validation should show the exact call path, how retries are disabled, source-to-reservation reconciliation and whether a browser retry can send a second release. C-19's narrow duplicate test is relevant but does not settle human double-click behavior or production rollback. Mode B uses the existing manual warehouse process; it would still need Vela business approval and correct order diversion, but it would not establish that RelayGrid's contracted automated workflow has passed acceptance.

Mira may take the design to the 15:00 session and ask Nia and Ivo for a written operational classification. Sera would need an understandable proposal distinguishing the two modes and staffing load before any commercial use. Customer consent cannot resolve RelayGrid's internal authority split by itself. Equally, an internal exception cannot authorize Vela's operators to take business risk without Sera's agreement. It is possible to prepare a draft while leaving execution conditional, but a promise that commercial work will start at a fixed time must reflect every remaining gate.

No work order has been sent to the production operations team. The queue remains disabled for commercial references. The final milestone is blocked. Ivo's interest in an efficient limited demonstration should not be read as a finding that the full implementation is complete, or as a refusal to consider a safer design. Ivo has asked that the classification decision identify the actual call path and the clause relied on, so the operations team can apply it to the configured mode.
