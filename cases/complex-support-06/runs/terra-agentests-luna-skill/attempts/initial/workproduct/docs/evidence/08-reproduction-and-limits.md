# E08 — Reproduced barriers and engineering investigation

Record version: ENG-614.4. Owner: Dan Vale. Last substantive update 2026-11-23 12:10 UTC. Environment: production-equivalent build 8.4, synthetic Rivermere applications, identical feature flags to intended launch.

Dan reproduced the error-path focus failure on Windows 11 with Firefox 144 and NVDA 2025.3 and reproduced an unreachable evidence-picker close control using keyboard navigation in Chrome 142. These are the environments tested, not a claim that the failure occurs only there. After rejecting an oversized file, the modal announces neither the error nor the remaining choices in the tested screen-reader session. Focus returns behind the modal. Repeated tab presses cycle background navigation, and the required declaration cannot be reached through the visible sequence. Refreshing restores the page but discards unsubmitted field edits in the current session.

The defect is in LanternPath's November 12 evidence component, not in the Trust's content. The integration agency cannot repair its keyboard event handling through theme settings. Disabling the evidence step would permit a draft to advance but would remove required evidence without an approved operational collection process. The backend receives no final submission in the reproduced failure, so a visible saved draft is not a received application. Dan has found no corruption of previously completed applications in the small test dataset. That does not prove absence of unrelated issues in every tenant or every browser.

The happy path works for Dan using a mouse with an accepted small file. A developer demonstration with that interaction cannot refute the reported failure. An automated scanner did not exercise the dialog after server-side file rejection; its clean report therefore does not contradict the manual result. Dan notes two further concerns: keyboard focus may be obscured by a sticky footer at high zoom, and receipt status is conveyed visually in one branch. Both are under examination. The present launch barrier is already knowable even if the full defect list is incomplete.

A patch branch replaces the modal behavior and adds an announced error summary. The earliest engineering target is November 26 for a testable build. Release depends on regression tests, deployment review and customer configuration checks; no fixed release or conformance date is committed. Dan can deliver a status report tomorrow at 12:00 even if the patch fails. He rejects the sales request to describe the patch as ready this afternoon. Product operations may evaluate a separate temporary flow, but its operation must not conceal that the main module is still blocked.

Support has the reproduction evidence it needs; it should not require the volunteer to repeat the same failure to make it valid. Additional voluntary testing can discover new issues and check alternatives, with fabricated files and respectful instructions. Dan will document tests that fail as well as those that pass. The report may be shared with Rivermere with tester aliases removed. It contains no diagnosis, medical history, actual grant evidence or recording of a private desktop. A more comprehensive assessment remains necessary before any broad claim about the full applicant service.
